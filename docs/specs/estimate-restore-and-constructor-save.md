# Восстановление и просмотр версий, сохранение конструктора

## Причины

POST rollback выполнял восстановление синхронно и достигал лимита HTTP 30 секунд. Read-only production-диагностика сметы 428 подтвердила POST 500 через 30 секунд.

После восстановления рабочей копии создавались новые позиции, но structure_cache_path продолжал указывать на снимок со старыми идентификаторами. У сметы 428 старые 2349 позиций удалены логически, новые 2349 активны; снимок остался прежним. POST bulk-update со старыми идентификаторами возвращал 404. Ошибку одновременно показывали API interceptor и экран сохранения.

## Поведение

- POST /api/v1/admin/estimates/{estimateId}/versions/{versionId}/rollback принимает Idempotency-Key (16–128 символов), возвращает 202 с сохранённой операцией. Повтор завершённой операции возвращает 200. Конфликт — 409, недоступная очередь — 503 с безопасным сообщением.
- Операции revision и restore используют существующие очередь estimate-revisions и ежедневный журнал. Одновременно допускается одна активная операция сметы. GET revisions/latest возвращает operation_type и target_version_id вместе с состоянием.
- Обработчик повторно проверяет организацию, права и исходную версию. До восстановления сохраняется pre_restore; восстановление и завершение операции атомарны. Повтор задания не создаёт новые снимки.
- Замена структуры и операции конструктора сбрасывают снимок. Миграция снимает ссылки на снимки смет, где позиции удалялись после последнего изменения заголовка; исходные файлы и версии не удаляются.
- Старые позиции при сохранении дают понятный 409. Отказ поиска записывается в журнал с контекстом операции без содержимого позиций. За уведомление о сохранении отвечает экран.
- «Открыть версию» показывает сохранённые разделы, вложенные позиции, количества, цены и суммы с поиском. Данные доступны только для просмотра. «Восстановить» — отдельное действие с подтверждением, в том числе для резервных снимков.

## Проверка и выпуск

Целевые PostgreSQL-тесты проверяют очередь, повторную доставку, повторную проверку прав, резервный снимок, сброс кеша и сохранение после замены позиций. Vitest проверяет контракт операции, уведомления и просмотр вложенной структуры. Выпуск через штатные backend/admin workflow после успешных проверок; production-проверки только read-only.
