# Каталог спецификаций: граница организации

## Проблема

Глобальный API каталога возвращает все спецификации без ограничения по текущей организации. Таблица `specifications` не содержит владельца, поэтому принадлежность определяется через связанные договоры в `contract_specification`. Отвязанные записи не имеют доказуемого владельца и не должны быть доступны ни одной организации.

Форма каталога отправляет `contract_id`, но backend его игнорирует. В результате создаются новые отвязанные записи, а UI пытается вывести отсутствующий `contract_id` как `#undefined`.

## Целевой контракт

- Любое чтение, изменение и удаление спецификации из глобального каталога разрешено только если она связана хотя бы с одним договором текущей организации.
- В ответах каталога загружаются только договоры текущей организации; UI показывает их бизнес-номера.
- Создание из глобального каталога требует один доступный договор текущей организации и атомарно создаёт и привязывает спецификацию к нему.
- Изменение реквизитов спецификации не меняет её связи с договорами. Управление связями остаётся в договорном workflow.
- Привязка существующей спецификации к договору разрешена только для спецификации, уже принадлежащей той же организации.
- Отвязанные legacy-записи скрываются: без отдельного поля владельца безопасно определить их организацию невозможно.
- Маршруты каталога используют существующие права `specifications.view/create/edit/delete`.

## Проверки

- PostgreSQL-регрессия на изоляцию списка, чтения, изменения и удаления.
- PostgreSQL-регрессия на атомарное создание с привязкой и запрет чужого договора.
- Контрактная проверка ответа: связанные договоры представлены бизнес-номерами, а не внутренним ID.
- Frontend-регрессия: в таблице нет `#undefined`, создание требует договор, редактирование не обещает изменение связи.
