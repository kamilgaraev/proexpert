# Складские резервы: стоимость, единицы и контекст проекта

## Проблема

Резервирование переводит количество из доступного остатка в зарезервированный, но не меняет физический запас и его стоимость. Production-проверка выявила три нарушения этого инварианта:

- стоимость агрегированного остатка рассчитывается только по доступному количеству и меняется при резервировании;
- список резервов теряет единицу измерения материала и подставляет `шт`;
- быстрый диалог незаметно использует глобально выбранный проект и дублирует централизованное уведомление API.

## Канонические инварианты

1. `total_quantity = available_quantity + reserved_quantity`.
2. `total_value = Σ((available_quantity + reserved_quantity) × unit_price)` по всем партиям материала.
3. `average_price = total_value / total_quantity` при ненулевом физическом остатке.
4. Резервирование и снятие резерва не меняют `total_quantity`, `total_value` и `average_price`.
5. Единица резерва берётся из `material.measurementUnit`: сначала человекочитаемое сокращение, затем полное название; технический fallback допускается только при действительно отсутствующем справочнике.
6. Если быстрый диалог использует глобальный проект, он явно показывает название проекта и источник контекста до подтверждения операции.
7. Стандартизированный API-ответ показывает одно централизованное уведомление; компоненты не создают второй toast об успехе или ошибке.

## API-контракт

Агрегированный складской остаток сохраняет существующие поля, но их смысл фиксируется:

- `available_quantity` — свободно для новых операций;
- `reserved_quantity` — удерживается активными резервами;
- `total_quantity` — физически находится на складе;
- `total_value` — стоимость всего физического остатка, включая резерв;
- `average_price` — средневзвешенная цена всего физического остатка.

`GET /api/v1/admin/advanced-warehouse/reservations` и ответ создания резерва возвращают `material.unit` из канонической единицы измерения материала. Связь загружается заранее, чтобы контракт не создавал N+1 запросы.

## UI-состояния

- При выбранном проекте диалог показывает: «Операция будет выполнена для проекта … Проект выбран в верхней панели».
- Без выбранного проекта диалог явно показывает: «Операция будет выполнена без привязки к проекту».
- При смене глобального проекта и повторном открытии диалога отправляется актуальный проект, а не значение первого рендера.
- После стандартизированного ответа остаётся только сообщение общего API-слоя — как для успеха, так и для ошибки.
- Ответ устаревшего запроса списка игнорируется после смены склада или фильтра и не может подменить текущий контекст.

## Проверки

- Backend-регрессия: стоимость и средняя цена неизменны до резерва, после резерва и после частичного снятия.
- Backend-регрессия: список и ответ создания резерва возвращают единицу материала.
- Frontend-регрессия: быстрый диалог показывает проект, отправляет актуальный `project_id` и не вызывает локальный success-toast.
- Frontend-регрессия: расширенный диалог и полное снятие резерва не вызывают локальный success-toast.
- Frontend-регрессия: стандартизированные API-ошибки не дублируются локальным уведомлением, а ответ предыдущего склада не перезаписывает актуальный список.
- Production: повторить резерв и частичное снятие, проверить постоянную стоимость, правильную единицу, один toast и явный проектный контекст.

## Риски и совместимость

- Структура ответов не меняется, корректируется смысл уже существующих числовых полей и значение `material.unit`.
- Доступный остаток по-прежнему уменьшается при резерве; операции, которым нужен свободный объём, продолжают использовать `available_quantity`.
- Финансовые и складские карточки, использующие `total_value`, перестают ошибочно трактовать резерв как выбытие.
