# Счета, акты и QR СБП B2B через Точку

Проверено 16.10.2026 по официальной документации и OpenAPI Точки. Основной способ оплаты МОСТ — перевод с расчётного счёта юридического лица или ИП. ЮKassa остаётся отключённой.

## Возможности и разрешения JWT

| Разрешение в интерфейсе Точки | Решение | Назначение и ограничения |
| --- | --- | --- |
| Просмотр реквизитов | Включить | Проверка расчётного счёта и получателя. Методы счетов используют ReadAccountsBasic/ReadAccountsDetail. |
| Получение выписок | Включить | ReadStatements. Окончательное подтверждение поступлений и возвратов. |
| Создание счетов и документов | Включить | ManageInvoiceData. Создание счетов, актов, получение PDF; также доступно удаление документов. |
| Создание и получение вебхуков | Включить | Регистрация уведомлений для client_id. В OpenAPI у webhook-методов пустой список OAuth scopes; название разрешения берётся из интерфейса банка. |
| Настройка оплаты через СБП | Включить для B2B QR | EditSBPData для создания QR, ReadSBPData для чтения. Разрешение шире одного B2B QR: в API СБП присутствуют регистрация ТСП и возвраты по отдельным видам QR. МОСТ эти исходящие операции не вызывает. |
| Просмотр остатка по счёту | Не требуется | ReadBalances. Общий остаток не подтверждает оплату конкретного счёта. Можно добавить для отдельной финансовой панели. |
| Создание платёжных ссылок | Не требуется для B2B QR | MakeAcquiringOperation/ReadAcquiringData относятся к эквайрингу: карты, розничный СБП, реестры, возвраты и подписки. Дополнительный сценарий после согласования тарифа и фискализации. |
| Создание платежей | Не требуется | CreatePaymentForSign готовит исходящий платёж для подписания владельцем. Для приёма оплаты не нужен. |
| Подписание платежей | Не требуется | Операции с исходящими платёжными поручениями. Не подписывает счета или акты. Не выдавать ради документооборота. |

Уровни разрешений интерфейса и технические scopes нельзя считать взаимно однозначными без подтверждения банка. Выдавать доступ только компании МОСТ. Проверить текст согласия относительно личных счетов владельца. JWT и client_id хранить только в защищённой серверной конфигурации. При выпуске нового ключа проверить client_id и регистрацию уведомлений; обычное продление ключа сохраняет прежний набор разрешений по инструкции банка.

## Документы и подпись

Подтверждены публичные методы:

- `POST /invoice/v1.0/bills` — счёт; `GET /invoice/v1.0/bills/{customerCode}/{documentId}/file` — его PDF.
- `POST /invoice/v1.0/closing-documents` с `Content.Act` — акт; соответствующий `GET .../file` — PDF.
- Для закрывающего документа можно передать `documentId` родительского счёта. В OpenAPI это необязательное поле.
- Поддерживаются также накладная, счёт-фактура и УПД; МОСТ их автоматически не выпускает. АУСН и продажа доступа без НДС не требуют автоматически добавлять счёт-фактуру с НДС.
- Отправка документа на email и удаление поддерживаются, но текущий поток МОСТ сохраняет собственные уведомления и неизменяемый архив. Самовольное удаление банковского документа при отмене заказа не выполняется.

В публичном API не обнаружены метод подписания счёта/акта, передача КЭП, отправка через ЭДО и проверка подписи. Официальная инструкция предлагает подписывать счёт и ставить печать в интернет-банке, в разделе «Документооборот». Это не подтверждает автоматическое подписание КЭП через API и не делает любой скачанный PDF подписанным первичным документом.

МОСТ сообщает источник PDF и не подтверждает наличие подписи. Подписанный оригинал согласуется через поддержку и ЭДО/интернет-банк. Вызов недокументированного метода или права на подпись исходящих платежей не используются. Информационное уведомление о возврате остаётся отдельным локальным документом: API не описывает эквивалент такого уведомления; оно не выдаётся за корректировочный УПД или счёт-фактуру.

Документ фиксирует предоставление права использования и доступа в рамках действующей оферты, а не оказание будущих услуг. Опубликованная версия оферты и её хеш не переписываются задним числом при смене генератора PDF.

## Надёжность выпуска

Снимок покупателя, реквизитов, суммы, периода и оферты сохраняется до обращения в банк. Внешние запросы выполняются вне транзакции оплаты. Идентификатор документа Точки записывается до скачивания PDF. Повторное скачивание использует этот идентификатор и частный неизменяемый архив S3 в области организации.

Для создания документа публичная спецификация не описывает ключ идемпотентности или метод поиска ранее созданного документа по номеру. Поэтому:

1. До POST сохраняется состояние `creating`.
2. После успешного ответа сохраняется `provider_document_id`; сбой PDF/S3 допускает безопасное повторное скачивание.
3. Таймаут, неоднозначный ответ или прерванный процесс переводят выпуск в `creation_unknown`. Повторный POST автоматически запрещён.
4. При 401/403/429 установлен интервал повторной попытки; при ошибке данных 400/422 требуется проверка.
5. Оператор с правом управления платежами сверяет документ в Точке и подтверждает найденный идентификатор либо отсутствие документа. Решение и основание сохраняются. Наблюдатель не может разрешить повторный выпуск.

Исторические готовые локальные PDF сохраняются как `legacy_local`, с прежним путём и содержимым. Не выпущенные счета и акты направляются в Точку. Для банковских PDF используется отдельный путь, чтобы старый локальный файл не мог быть принят за файл банка.

Статус оплаты банковского счёта не используется как основание активации подписки: банк называет его визуальной подсказкой, допускающей ручное изменение и не покрывающей частичные/поздние оплаты и переплаты. Источник подтверждения — окончательно проведённая операция выписки с проверкой получателя, ИНН плательщика, бизнес-счёта, суммы и назначения. Повторное уведомление не создаёт повторную активацию.

## QR и ссылка СБП B2B

Официальный API отдельно поддерживает QR для юридических лиц и ИП. Это не розничный QR для личного банковского приложения физлица.

- Создание: `POST /sbp/v1.0/b2b-qr-code/merchant/{merchantId}/{accountId}`.
- Чтение изображения и параметров: `GET /sbp/v1.0/b2b-qr-code/{qrcId}`.
- В ответе создания доступны `qrcId` и ссылка `payload` на `qr.nspk.ru`. Для этой ссылки не нужен API эквайринговых платёжных ссылок.
- Сумма передаётся целым числом копеек, максимум 100 000 000 копеек (1 млн рублей). Назначение — до 140 символов. `ttl` — 1–129 600 минут; по умолчанию банк задаёт 72 часа.
- МОСТ задаёт сумму счёта, назначение с его номером, `takeTax=false`, срок не дольше срока оплаты и собственную связь счёта с QR. Изображение и ссылка проверяются перед выдачей клиенту.
- QR доступен управляющему биллингом для неоплаченного действующего счёта. После частичной оплаты используется доплата по реквизитам: ранее выданный QR может содержать исходную полную сумму.
- Уведомление `incomingSbpB2BPayment` содержит customerCode, qrcId, сумму и назначение; в опубликованном примере нет даты, paymentId или реквизитов плательщика. Оно только инициирует повторную сверку выписки. Само уведомление не даёт подписку.
- По официальной инструкции возвраты B2B QR выполняются в интернет-банке. API возвратов QR описан для динамических розничных кодов; не применять его к B2B.

Для запуска необходим зарегистрированный ТСП и его `merchantId`, согласованные условия именно СБП B2B и отдельное включение `TOCHKA_SBP_B2B_ENABLED`. Наличие прав JWT не доказывает подключение ТСП или согласие с тарифом. По умолчанию функция выключена до подтверждения владельцем подключения. `TOCHKA_SBP_MERCHANT_ID` не является секретным JWT, но берётся из подтверждённых данных банка.

## Комиссии и касса

Выбор разрешения JWT не равен заказу платного эквайринга. Отдельная цена за само разрешение в проверенной API-документации не указана. Банковское обслуживание, эквайринг, СБП и ЭДО имеют отдельные условия.

| Способ | Подтверждено | Что необходимо уточнить |
| --- | --- | --- |
| Обычный B2B перевод | Точка публикует бесплатные входящие и исходящие платежи на тарифах РКО | Действующий договор владельца, специальные ограничения и обслуживание счёта |
| СБП B2B QR | Отдельный API, оплата от компаний/ИП, ссылка и изображение QR | Комиссия получателя и плательщика, минимум/максимум, абонентская плата, доступность для SaaS и тариф подключённого ТСП |
| Эквайринговая ссылка: карта/розничный СБП | Приём платежей тарифицируется; ставка зависит от вида деятельности и оборота | MCC МОСТ, индивидуальная ставка с НДС, фискализация, возвраты, сроки выплат и прочие договорные расходы |
| Подписание и ЭДО | Подписание в интернет-банке описано; API подписи не опубликован | Тип подписи, юридическая сила конкретного файла, стоимость исходящих документов, КЭП/КриптоПро, наличие отдельного договорного API |

Рекламные ставки «от» и акции розничного СБП не являются подтверждённым тарифом СБП B2B для МОСТ. Тариф Банка России для банков также не равен комиссии клиента Точки. Не закладывать неподтверждённые 0%, 0,4% или 0,7% в расчёт окупаемости B2B QR.

ФНС разъясняет освобождение от ККТ при дистанционных безналичных расчётах через СБП между компаниями/ИП в рамках предпринимательской деятельности, без предъявления электронного средства платежа при непосредственном взаимодействии (п. 9 ст. 2 54-ФЗ). Публикация архивная: при изменении платёжного сценария проверить действующую норму. Оплату от физлица нельзя автоматически включать в это исключение. При подключении личных карт и розничного СБП требуется отдельная проверка ККТ и полного цикла чеков, включая возврат и зачёт предоплаты.

## Вопросы поддержке Точки

1. Поддерживается ли для нашего ИП, расчётного счёта и SaaS приём через API СБП B2B? Как получить действующий merchantId и проверить подключённый ТСП?
2. Каковы комиссии СБП B2B для получателя и плательщика, минимумы, лимиты, абонентская плата, условия возврата и НДС? Просим ссылку на действующий тариф/пункт договора.
3. Какие scopes выдаёт интерфейсное разрешение «Настройка оплаты через СБП»? Можно ли ограничить его B2B QR без розничных возвратов и регистрации посторонних ТСП?
4. Как в выписке выглядят B2B QR поступления: сохраняются ли ИНН и расчётный счёт плательщика, назначение и уникальный идентификатор? Возможны ли агрегированные зачисления? Нужен обезличенный пример.
5. Есть ли поддерживаемая идемпотентность POST счетов/актов/QR или поиск по номеру/собственному идентификатору, не отражённые в публичной OpenAPI?
6. Поддерживаются ли КЭП, отправка актов по ЭДО и проверка статуса подписи через отдельный API? Какой договор, тариф и доступ нужны? Чем подпись/печать в PDF отличается от КЭП и что вернёт GET file после ручного подписания?
7. Какие комиссии, MCC и стоимость фискализации будут при добавлении эквайринговых ссылок МОСТ с картой/розничным СБП? Есть ли фиксированная плата при отсутствии операций?
