# Область сравнения предложений по заявке на закупку

## Контекст

МОСТ позволяет сравнивать коммерческие предложения не только внутри одного запроса поставщику, но и по всей заявке на закупку. В таком раунде предложения принадлежат разным запросам поставщика, однако одной организации, проекту и заявке на закупку.

Production-сценарий с двумя запросами поставщика завершился HTTP 500 при выборе победителя. Транзакция была отменена PostgreSQL-проверкой `procurement award candidate event scope mismatch`: событие аудита закрепляет запрос выбранного предложения, а существующий DB-инвариант ошибочно требует тот же запрос у каждого кандидата.

## Требуемый контракт

- Область доказательства определяется составом неизменяемого манифеста:
  - `supplier_request` — все кандидаты принадлежат одному запросу поставщика;
  - `purchase_request` — кандидаты принадлежат нескольким запросам поставщика одной заявки на закупку.
- Для `supplier_request` PostgreSQL продолжает запрещать кандидатов из соседнего запроса.
- Для `purchase_request` PostgreSQL разрешает разные запросы поставщика только внутри той же организации, проекта и заявки на закупку.
- Запрос поставщика на событии остаётся запросом выбранного предложения; выбранная пара и её версия должны присутствовать в манифесте.
- Область входит в fingerprint и source hash новых межзаявочных событий.
- Старые события и повтор supplier-request-сценария сохраняют прежние hash-контракты.
- Область `purchase_request` допустима только при наличии как минимум двух разных запросов поставщика в манифесте.

## Проверки

- Регрессионный PostgreSQL-тест воспроизводит выбор по заявке на закупку с кандидатами из двух запросов поставщика.
- Существующая защита от подмешивания кандидата в supplier-request-событие остаётся зелёной.
- Проверяются миграционный контракт, DTO/hash-контракт и минимальный статический анализ изменённых PHP-файлов.

## Риск и совместимость

Изменение не ослабляет tenant/project/purchase-request lineage. Новая колонка получает безопасное значение `supplier_request` для существующих записей. Межзаявочная область вычисляется только при фактическом наличии нескольких запросов, поэтому уже записанные одно-заявочные события остаются идемпотентными.
