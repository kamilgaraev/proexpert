# Единая модель scope для канонических отчётов

## Проблема

Авторизация отчётов всегда проверяет разрешение одновременно в контексте организации и каждого проекта. Проектная роль корректно разрешает выбранный проект, но не может разрешить искусственно добавленный организационный факт, поэтому запуск завершается `REPORT_SCOPE_FORBIDDEN`.

## Контракт

- Организация является границей tenant и проверяется независимо через активное членство.
- Разрешения проверяются на наиболее конкретных фактах фактического scope отчёта.
- Для scope без проектов и ресурсов используется организационный факт.
- Для project scope используются факты всех проектов; организационная роль наследуется ABAC-проверкой на проектный факт.
- Для resource scope используются ресурсные факты, а проектные факты добавляются только для проектов, не представленных ресурсами.
- Все факты scope должны быть разрешены. Расширение scope одним недоступным проектом запрещает операцию целиком.
- Одна модель применяется к каталогу, запуску, повторной авторизации run, rows, drill-down и export.

## Проверки

- чистая unit-матрица построения permission facts;
- интеграционный тест проектной роли без организационного grant;
- сохранение отказа для чисто организационного scope без организационного grant;
- существующие тесты точного scope, race safety, run/rows/export authorization;
- синтаксис, Larastan и контрактные тесты маршрутов.

## Риски

Нельзя просто убрать организационную проверку членства: она остаётся обязательной tenant-границей в `activeActor`. Нельзя применять правило «достаточно одного проекта»: разрешение требуется для каждого наиболее конкретного факта scope.
