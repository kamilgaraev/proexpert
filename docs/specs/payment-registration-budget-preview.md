# Предварительная проверка бюджета при регистрации оплаты

## Проблема

Карточка платежного документа показывает бюджетный лимит для плановой даты документа. В диалоге фактической оплаты пользователь выбирает собственные сумму и дату, а сервер проверяет лимит уже для месяца фактической даты. При разных месяцах интерфейс может показывать «Лимит доступен», хотя регистрация гарантированно будет отклонена.

## Контракт

- Admin API принимает идентификатор платежного документа, сумму и дату фактической оплаты.
- Проверка использует ту же операцию `payment_register`, тот же расчет месяца и те же правила лимита, что и окончательная регистрация.
- Предварительная проверка не создает проверку лимита, резерв, транзакцию или аудит и не изменяет документ.
- Ответ возвращается стандартным `AdminResponse` и содержит существующий объект `budget_limit_check`.
- Доступ защищен тем же правом регистрации оплаты и организационным контекстом документа.

## Состояния UI

- При открытии и после изменения суммы или даты диалог запрашивает актуальную проверку.
- Во время запроса показывается нейтральное состояние проверки.
- Полученный результат полностью заменяет документный индикатор лимита в диалоге.
- При решении `block` кнопка регистрации недоступна, а пользователь видит серверную причину до отправки.
- При временной ошибке предварительной проверки интерфейс не выдает ложное разрешение и предлагает повторить проверку.
- Окончательная регистрация сохраняет серверную проверку внутри транзакции как обязательную границу безопасности.

## Проверки

- Backend: один документ дает разные результаты для разных месяцев; предварительный запрос ничего не записывает.
- Frontend: выбранная дата и сумма передаются в preview API; блокирующий результат отключает регистрацию и заменяет исходный «доступный» индикатор.
- Сквозная production-проверка: дата в августе показывает блокер августа до отправки, дата в сентябре использует сентябрьский лимит.
