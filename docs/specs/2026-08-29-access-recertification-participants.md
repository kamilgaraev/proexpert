# Участники пересмотра доступов

## Проблема

Форма кампании требует ручные внутренние идентификаторы, а сервер проверяет их глобально по таблице пользователей. В результате интерфейс раскрывает технические ID, а подмена запроса позволяет связать кампанию, проверку или отзыв доступа с пользователем другой организации.

## Контракт

- Владелец кампании, получатель эскалации, проверяющий и ответственный за отзыв выбираются только из активных сотрудников текущей организации.
- HTTP-валидация отклоняет отсутствующего, неактивного и относящегося к другой организации пользователя с кодом 422.
- Сервисный слой повторяет проверку перед записью, чтобы граница сохранялась вне HTTP-контроллера.
- Пользовательские выборки используют существующий организационно-ограниченный endpoint `/users/options`.
- В интерфейсе отображаются имя и электронная почта; внутренний ID не вводится и не используется как резервная подпись.
- Термин `evidence` в пользовательском интерфейсе заменяется на «аудиторские данные» или «выгрузка для аудита».

## Проверки

- Backend: успешное создание с активным сотрудником своей организации; отказ для чужого пользователя через HTTP и при прямом вызове сервиса.
- Frontend: варианты сотрудников загружаются из организационного endpoint; форма отправляет выбранные ID, но не показывает поля ID; термин `Evidence` отсутствует.
