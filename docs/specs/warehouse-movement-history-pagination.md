# Пагинация истории складских движений

## Проблема

`GET /api/v1/admin/warehouses/{warehouse}/movements` принимает на клиенте `page` и `per_page`, но backend игнорирует параметры и возвращает все движения склада одним массивом. В результате время ответа и потребление памяти растут вместе со всей историей, а UI не может показать точное количество страниц и выполнить поиск по полной истории.

## Контракт API

Endpoint возвращает стандартный `AdminResponse` с пагинированными данными:

- `data` — движения текущей страницы;
- `meta.current_page`, `meta.last_page`, `meta.per_page`, `meta.total`, `meta.from`, `meta.to`;
- `links.first`, `links.last`, `links.prev`, `links.next`.

Поддерживаемые параметры:

- `movement_type` — допустимый тип складского движения;
- `date_from`, `date_to` — границы периода;
- `search` — поиск по материалу, коду материала, документу, проекту, пользователю и основанию;
- `page` — номер страницы, минимум 1;
- `per_page` — размер страницы от 1 до 100, по умолчанию 20.

Ответ остаётся совместимым с `normalizePaginatedResponse` в админке.

## Backend

- HTTP-валидация размещается в отдельном FormRequest.
- Контроллер только нормализует контекст склада, вызывает сервис и возвращает `AdminResponse`.
- Запрос ограничивается организацией и складом, использует eager loading и пагинацию на уровне PostgreSQL.
- Сериализация одной строки переиспользуется для пагинированного и внутреннего непагинированного сценариев.

## Админка

- История списаний загружает одну страницу по 20 строк.
- Поиск выполняется сервером по всей истории с задержкой перед запросом.
- UI показывает точное общее количество операций и диапазон текущей страницы.
- Доступны переходы между страницами; смена склада или поискового запроса возвращает на первую страницу.
- После успешного списания обновляются первая страница истории и остатки.

## Ошибки и состояния

- При ошибке история не подменяется состоянием «записей нет» без сообщения.
- Пустой результат поиска отличается от полностью пустой истории.
- Во время загрузки повторные переходы по страницам блокируются.
- Если после обновления текущая страница стала недоступна, UI возвращается на последнюю доступную страницу.

## Проверки

- Backend feature-тесты: валидация, изоляция организации, пагинация, фильтр типа и поиск.
- Admin Vitest: параметры запроса, точный счётчик, поиск, навигация, пустой результат.
- PHPStan изменённых PHP-файлов, `php -l`, TypeScript, ESLint и Prettier.
- Backend деплоится раньше admin, затем выполняется постдеплойная проверка обоих релизов.
