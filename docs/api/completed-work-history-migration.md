# Переход истории объёмов выполненных работ

Статус: T27 реализована в рабочей ветке. Сверка остаётся только для чтения; преобразование выполняется отдельной операцией. В рабочую систему изменения не выпущены.

## Зачем это нужно

У выполненной работы исторически было два поля объёма: `quantity` и `completed_quantity`. Разные отчёты брали разные значения. После перехода у факта одно производственное количество. Автоматически переписывать исторические суммы и подписанные акты нельзя.

Оба поля по-прежнему **читаются**. Обычная запись (создание, изменение, удаление, подтверждение) не обходит действующие запреты: подтверждённый, журнальный или включённый в акт факт по-прежнему правится только через корректировку основания, а не через старые поля в обход сверки.

## Категории сверки

Сверка проекта: `GET /api/v1/admin/projects/{project}/works/reconciliation` (право просмотра выполненных работ). Ответ не меняет данные.

| Категория | Как выглядит | Автоматически | Вручную |
| --- | --- | --- | --- |
| Совпадают | Оба значения корректны и равны | Протокол «уже канон», поля не трогаются | Не требуется |
| Заполнено только `quantity` | `completed_quantity` пусто | Оба поля получают это количество; оригинал пустого значения хранится в протоколе | Если запись защищена актом или приёмкой — только вручную |
| Заполнено только выполненное | В классификаторе нет `quantity`, есть корректный выполненный объём | Оба поля получают выполненный объём | Если запись защищена — только вручную, без правки оригинала |
| Оба заданы и различаются | Конфликт 100 и 10 | Ничего не выбирается | Решение с причиной: какое поле канон или явное значение |
| Некорректный объём | Отрицательное, слишком большое, не число | Ничего не угадывается | Только явное корректное значение |
| Дубль журнального объёма | Несколько фактов на один объём журнала | Количество не переписывается | Разбор дубля; это не молчаливый выбор поля |
| Связь с актом или приёмкой | Подписанный/утверждённый акт или принятый объём приёмки | Поля факта не меняются | Решение фиксируется в протоколе; оригинал и подпись акта не трогаются |
| Уже обработано | Есть протокол преобразования | Повтор ничего не дописывает и не меняет строку | Повтор того же ключа возвращает исходный протокол |

## Что делается автоматически

Команда штатного перехода (только выбранные организация и проект, без прогона «по всей базе»):

```
php artisan completed-works:transform-history --organization=ID --project=ID
```

Сначала осмотр без записи:

```
php artisan completed-works:transform-history --organization=ID --project=ID --dry-run
```

Тот же прогон доступен как `POST /api/v1/admin/projects/{project}/works/reconciliation/transform` (право редактирования). Параметр `dry_run` включает осмотр. Страницы задаются как у сверки: `after_id`, `batch_size`.

Автоматически обрабатываются только однозначные случаи без защищённой истории. В протоколе всегда есть исходные значения, правило, автор (если вызов из API), время и версия правила `t27-v1`. Повторный запуск не создаёт вторую строку протокола и не меняет уже обработанные факты.

## Уникальный индекс на объём журнала

Миграция `2026_09_20_020000_add_unique_active_journal_work_volume_fact` при деплое **не чинит дубли** и **не удаляет** строки факта. Если на момент миграции уже есть несколько активных фактов на один `journal_work_volume_id`, уникальный индекс просто не создаётся, а деплой продолжается.

После ручной сверки и разбора дублей включите индекс отдельно:

```
php artisan completed-works:ensure-active-journal-volume-unique-index
```

Команда создаёт частичный уникальный индекс только когда дублей нет. Если дубли остались — отказывается с понятным сообщением и ничего не меняет. Повторный запуск после успешного создания безопасен (`IF NOT EXISTS`).

## Когда остановиться

Остановитесь, если в сверке или в итоге команды `skipped_manual` больше нуля / `stop_on_discrepancy` истинно:

- конфликт двух заполненных объёмов;
- подписанный или утверждённый акт, принятый объём приёмки;
- дубль журнального объёма;
- некорректное число.

Не запускайте следующий проект и не считайте переход законченным, пока эти строки не разобраны. Не выбирайте поле «как в последнем отчёте» без причины. Не включайте уникальный индекс, пока сверка по дублям журнального объёма не чистая.

Ручное решение: `POST /api/v1/admin/projects/{project}/works/reconciliation/decisions/{completed_work}`. Нужны ключ операции, текущая версия записи, причина не короче десяти символов и источник (`quantity`, `completed_quantity` или `explicit` с каноническим количеством). Повтор того же тела и ключа возвращает исходный протокол. Другое тело с тем же ключом — конфликт.

Для защищённой истории решение **записывается в протокол**, а поля факта, строки акта, файл подписи и редакции **не изменяются**. Конфликт в сверке остаётся видимым. Для незащищённой неоднозначной записи оба поля факта приводятся к выбранному канону, оригинал остаётся в протоколе. Сумма и цена факта этим прогоном не пересчитываются.

## Обратный режим чтения

Обратный режим — это чтение исходных полей и протокола, а не откат базы.

- API по-прежнему отдаёт `quantity` и `completed_quantity`.
- Протокол преобразования, корректировки, версии документов и подписи не удаляются.
- Команда с `--dry-run` ничего не пишет и ничего не стирает.

Разрушительный откат данных (удаление протоколов, правка подписанных актов, возврат полей «как было всем скопом») штатной процедурой не является и не рекомендуется: он уничтожает след решения и может разойтись с уже выданными документами.
