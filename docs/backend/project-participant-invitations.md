# Приглашение организации в проект

Приглашение участника проекта создаёт администратор проекта. Организация заказчика регистрируется в общем личном кабинете как самостоятельная организация: первый пользователь получает роль `organization_owner`, а организация управляет собственными подпиской, модулями и командой. Роль `customer` назначается только связи организации с проектом (`project_organization`); она не является ролью пользователя и сама по себе не выдаёт права владельца или администратора.

## Сценарий

1. Администратор создаёт приглашение с ролью проекта и email; для уже зарегистрированной организации указывается её ID. Срок действия — 7 дней.
2. Новое письмо ведёт на `/project-invitations/{token}` общего личного кабинета. Старые ссылки и `/api/v1/customer/...` API остаются доступны для уже отправленных приглашений.
3. `GET /api/v1/landing/project-participant-invitations/{token}` показывает статус, проект, роль и название адресованной организации (если есть). Email и ИНН в публичном ответе не раскрываются.
4. Новый владелец регистрируется обычной формой ЛК. Отложенный `CompleteRegistrationSideEffects` принимает совпавшее по email/ИНН приглашение идемпотентно. Если фоновый процесс ещё не завершился, владелец после входа может явно принять приглашение через POST.
5. Для уже существующей организации приглашение принимает только её активный владелец с ролью `organization_owner`; совпадение адреса контактного email организации с email владельца не требуется. Чужая организация не может принять приглашение. Если приглашение содержит ИНН новой организации, отсутствующий или отличный ИНН отклоняется.

`POST /api/v1/landing/project-participant-invitations/{token}/accept` требует обычную проверенную LK-сессию, выбранную организацию и owner membership. При успехе организация добавляется к проекту с приглашённой проектной ролью. Истёкший, отменённый или уже принятый другим участником токен не может изменить участие.

## Старые customer-аккаунты

Старый отдельный customer flow создавал пользователей с ролью `customer_owner`. Автоматическое повышение этой роли до `organization_owner` не выполняется: оно расширяет права и может затронуть организационные данные и биллинг. Для старых аккаунтов нужна отдельная адресная проверка владельца и ручная/узко ограниченная миграция после подтверждения полномочий; массовое повышение запрещено.
