# Архитектура файлового хранилища МОСТ в Timeweb Cloud S3

**Статус:** согласовано к реализации 6 августа 2026 года

**Область:** Laravel backend МОСТ (`prohelper`) и админка МОСТ (`prohelper_admin`) как клиент multipart API

**Поставщик:** Timeweb Cloud S3
**Бакет:** один приватный бакет `prohelper-storage`

## 1. Цель

Полностью отказаться от Yandex Object Storage и устаревшей схемы с отдельными дисками и условными бакетами. Все актуальные файлы МОСТ должны храниться в одном приватном бакете Timeweb Cloud S3, иметь организационно изолированные неизменяемые ключи и обслуживаться через единый серверный шлюз `App\Services\Storage\FileService`.

Старые объекты не переносятся. Связанные со старыми файлами записи базы данных удаляются, потому что production ещё не содержит ценных пользовательских файлов. Система начинает работу с пустого бакета и новой схемы ключей.

## 2. Принятые решения

- Используется только `prohelper-storage`; отдельные бакеты и Laravel-диски `reports` и `personals` удаляются.
- Бакет приватный. Публичный ACL объектов не используется.
- Все актуальные ключи начинаются с `org-{organization_id}/` и обязательно содержат сегмент актора: `user-{user_id}` для пользовательского действия либо `user-system` для системного действия.
- Объекты получают уникальные неизменяемые ключи; перезапись бизнес-объекта по тому же ключу запрещена.
- Целостность фиксируется SHA-256 и доменным аудитом в БД. Бизнес-логика не зависит от S3 `VersionId`.
- Версионирование бакета остаётся включённым как инфраструктурная страховка, но не является частью прикладного контракта.
- Обычные небольшие загрузки проходят через backend. Крупные IFC и другие тяжёлые объекты загружаются напрямую в S3 multipart-частями по короткоживущим presigned URL.
- Скачивание выполняется по короткоживущим presigned URL после серверной авторизации.
- Автоматическое удаление отчётов отключается. Отчёты хранятся бессрочно и удаляются только явным действием пользователя или администратора.
- Старые команды глобального сканирования и удаления объектов удаляются.
- Новая CI/CD-инфраструктура, прокси-хранилище, второй бакет и fallback на Яндекс не создаются.
- Холдинги, сайты холдингов и CMS не рефакторятся в рамках этой миграции.

## 3. Целевая структура ключей

```text
prohelper-storage/
└── org-{organization_id}/
    ├── reports/exports/{export_uuid}/user-{user_id}/{object_uuid}.{ext}
    ├── personal-files/user-{user_id}/{object_uuid}.{ext}
    ├── legal-archive/{document_uuid}/user-{user_id}/{object_uuid}.{ext}
    ├── quality-control/{entity_uuid}/user-{user_id}/{object_uuid}.{ext}
    ├── estimates/{entity_uuid}/user-{user_id}/{object_uuid}.{ext}
    ├── design-models/{package_uuid}/user-{user_id}/{object_uuid}.{ext}
    ├── acts/{entity_uuid}/user-{user_id}/{object_uuid}.{ext}
    └── temporary/{purpose}/user-system/{object_uuid}.{ext}
```

Правила ключа:

1. `organization_id` и `user_id` берутся только из авторизованного серверного контекста; для системного действия backend подставляет только фиксированный сегмент `user-system`.
2. Имя загруженного пользователем файла не входит в ключ и хранится отдельно как `original_name`.
3. Идентификатор объекта — UUID/ULID, созданный backend до загрузки.
4. Расширение строится из разрешённого MIME-типа, а не из произвольного имени клиента.
5. Нормализация запрещает `..`, пустые сегменты, обратные слеши, управляющие символы и ключи вне `org-{id}/`.

## 4. Компоненты backend

### 4.1 `FileService`

`FileService` становится единственной прикладной точкой работы с S3 и предоставляет:

- запись приватного объекта и потоковую запись;
- получение метаданных и потоковое чтение;
- короткоживущую ссылку на скачивание;
- запуск multipart-сессии;
- presigned URL для конкретной multipart-части;
- завершение и отмену multipart;
- явное удаление актуального ключа;
- проверку организационной области ключа;
- проверку размера, MIME, ETag и SHA-256.

Доменные сервисы хранят собственные записи и передают `FileService` готовый организационный ключ. Прямые вызовы `Storage::disk(...)`, ручное создание `S3Client` и выбор бакета из бизнес-модулей удаляются.

### 4.2 `OrganizationStoragePath`

Небольшой value object строит и валидирует ключи. Он не обращается к БД и S3. Это исключает расхождение форматов между отчётами, персональными файлами и крупными загрузками.

### 4.3 Multipart-сессии

Для крупных загрузок сервер создаёт устойчивую запись с состоянием:

```text
initiated -> uploading -> verifying -> completed
                       \-> failed
                       \-> aborted
```

Запись содержит организацию, пользователя, назначение, ключ, S3 upload id, ожидаемые размер/MIME/SHA-256, размер части, срок действия и итоговые метаданные. Backend подписывает только разрешённые номера частей. После `CompleteMultipartUpload` отдельная существующая очередь вычисляет или подтверждает SHA-256 и только затем делает объект доступным доменному сценарию.

Повторный запрос завершения идемпотентен: он возвращает уже завершённый результат либо продолжает проверку. Просроченная незавершённая сессия отменяется прикладной командой, а инфраструктурное правило Timeweb удаляет незавершённые multipart-загрузки через один день.

## 5. Прикладные данные

Единой таблицы всех файлов не создаётся. Каждый домен хранит только необходимые ему данные:

- `storage_key`;
- `original_name`;
- `mime_type`;
- `size_bytes`;
- `sha256`;
- `created_by_user_id`;
- доменные идентификаторы и аудит.

Поля `artifact_version_id`, `storage_version_id` и аналоги, которые содержат именно S3 `VersionId`, удаляются из прикладных контрактов и схемы. Доменные `document_version_id`, `estimate_version_id` и другие бизнес-версии не затрагиваются.

Перед удалением старых S3-полей миграция удаляет неценные файловые записи и зависимые технические записи в порядке внешних ключей. Одноразовый reset также удаляет бумажные юридические подписи вместе с legacy signature storage state; это необратимо и явно принято владельцем как старт с нуля, поскольку реальных пользователей и ценных production-данных не было. Будущие подписи этот reset не затрагивает. Исходные бизнес-данные, из которых можно заново сформировать отчёт или документ, не удаляются за исключением этой подтверждённой legacy signature boundary.

## 6. Laravel и окружение

Единственный S3-диск `s3` использует:

```dotenv
FILESYSTEM_DISK=s3
MOST_S3_ACCESS_KEY_ID=
MOST_S3_SECRET_ACCESS_KEY=
MOST_S3_REGION=ru-1
MOST_S3_BUCKET=prohelper-storage
MOST_S3_ENDPOINT=https://s3.twcstorage.ru
MOST_S3_USE_PATH_STYLE_ENDPOINT=true
MOST_S3_DOWNLOAD_TTL_SECONDS=300
MOST_S3_UPLOAD_TTL_SECONDS=900
```

Конфигурация не содержит значений Yandex Object Storage по умолчанию. Переменные общего AWS-пространства не используются файловым хранилищем, чтобы не пересекаться с SES, SQS или DynamoDB при их возможном включении.

При production-конфигурации отсутствие обязательной `MOST_S3_*` переменной должно приводить к явной ошибке запуска, а не к незаметному переключению на локальный диск или другой endpoint.

## 7. Права, ключи и CORS

- Runtime-ключ принадлежит отдельному дополнительному пользователю Timeweb с доступом Read + Write только к `prohelper-storage`.
- Администраторский ключ не хранится в `.env` приложения и используется только владельцем инфраструктуры.
- Секреты не попадают в Git, логи, ответы API, параметры команд и документацию.
- После завершения миграции временный runtime-ключ ротируется пользователем.
- CORS бакета разрешает только фактические HTTPS-origin админки и личного кабинета МОСТ.
- Разрешённые методы для прямой загрузки: `PUT`, `POST`, `HEAD`; для проверки/скачивания — `GET`, `HEAD`.
- Разрешённые headers ограничиваются заголовками multipart/presigned-запросов и `Content-Type`; credentials браузера не используются.
- `ExposeHeaders` включает `ETag`, необходимый для завершения multipart.
- CDN и публичные домены бакета не включаются.

## 8. Жизненный цикл

В Timeweb настраиваются два инфраструктурных правила:

1. Удаление незавершённых multipart-загрузок через 1 день.
2. Удаление неактуальных версий объектов через 30 дней.

Текущие версии объектов автоматически не удаляются. Laravel scheduler не удаляет отчёты по возрасту. Явное пользовательское удаление создаёт delete marker; инфраструктурное правило позднее очищает неактуальные версии.

## 9. Переключение и откат

Миграция выполняется последовательными deploy-блоками, каждый из которых совместим с пустым Timeweb-бакетом:

1. Единая конфигурация `MOST_S3_*` и рабочий диск Timeweb.
2. Единый шлюз и организационные ключи для обычных файлов.
3. Прямой multipart и проверка целостности крупных файлов.
4. Удаление старых дисков, сервисов, команд и Yandex AI/Object Storage кода.
5. Очистка неценных файловых записей и удаление зависимости от S3 `VersionId`.

После destructive reset откат допускается только на Timeweb-совместимый релиз МОСТ с `caf3a815d1cf706b0ed3ea86b0bb7d56716726eb` (hotfix PR #254) или более новый, с текущими `MOST_S3_*` и тем же бакетом `prohelper-storage`. Запрещены rollback миграции, восстановление старых файловых или signature-записей, Yandex fallback, второй бакет и публичный доступ.

## 10. Проверка

Для каждого блока обязательны:

- целевые unit/feature-тесты с fake S3 или записывающим SDK-клиентом;
- Larastan по изменённым backend-файлам;
- архитектурный тест, запрещающий новые прямые S3-вызовы вне слоя хранения;
- проверка config cache с полным набором `MOST_S3_*` и проверка отказа при неполном наборе;
- проверка PR и штатного deploy workflow;
- read-only production-smoke: версия релиза, отсутствие новых S3-ошибок в логах, доступность health endpoint;
- отдельный реальный smoke Put/Head/Get/Delete в тестовом `org-{id}/temporary/smoke/user-system/{object_uuid}` через прикладной API или безопасную команду релиза без вывода секрета.

## 11. Что выполняется без простоя

Без простоя выполняются изменения конфигурации, перевод сервисов на единый диск, добавление новых API multipart, отключение scheduler-задач, удаление legacy-кода и очистка пустых/неценных файловых таблиц. Реальных пользователей и ценных production-файлов сейчас нет, поэтому двойная запись, копирование объектов и окно maintenance не нужны.

## 12. Что требует внешнего доступа к Timeweb

Только владелец Timeweb выполняет или подтверждает:

- создание/ротацию дополнительного пользователя и ключа бакета;
- CORS для реальных frontend-origin;
- lifecycle для незавершённых multipart и неактуальных версий;
- сохранение включённого versioning;
- отсутствие публичного доступа и CDN.

Код, PR, merge, штатный deploy и production-smoke выполняются автономно без ручного деплоя.
