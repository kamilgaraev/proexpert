# Очередь решений по технике — дизайн исправления

## Цель и границы

Администратор с правом `machinery-operations.requests.create` должен создавать заявку на технику прямо на странице «Техника и оборудование». Диспетчер с правом `machinery-operations.requests.approve` должен видеть все заявки, по которым ещё можно принять решение, выбрать конкретную заявку и конкретную canonical-физическую единицу и назначить её. Изменения ограничены backend и admin; storage, legacy rollback path, CI/CD и mobile не меняются.

## Единый смысл «требует решения»

Заявка требует решения, пока её статус равен `pending` или `approved`: обе стадии допускают назначение в `AssetDispatchService`. Модель получает scope `requiresDecision()`. Список принимает явный фильтр `requires_decision=1`, а overview использует тот же scope. Это исключает расхождение между счётчиком и таблицей и не превращает UI в источник бизнес-правила.

## Создание заявки

Admin открывает собственный dialog по кнопке «Создать заявку на технику». В форме есть проект, плановое начало, необязательный конец, цель работ, приоритет и четыре необязательных требования к эксплуатационному профилю: учёт наработки, топлива, выработки и технического обслуживания. В payload попадают только отмеченные требования со значением `true`; неотмеченный параметр не ограничивает подбор. Технические ID, материалы, складские поля и schedule task пользователю не показываются.

Backend продолжает принимать запрос через существующие `CreateAssetRequest`, `AssetRequestData` и `AssetDispatchService`. Route middleware проверяет permission, а service — project/organization scope. После успеха admin инвалидирует очередь и overview, поэтому заявка появляется без перезагрузки страницы.

## Permissions и диспетчер

Кнопка и dialog создания существуют только при `machinery-operations.requests.create`. Выбор заявки, загрузка кандидатов и подтверждение назначения доступны только при `machinery-operations.requests.approve`. Route middleware остаётся обязательной серверной защитой.

Кандидаты привязаны к выбранному `request.id`; выбор хранит конкретный `candidate.asset.id`, а mutation отправляет его `organization_asset_id`. Индексные обращения к первому элементу не используются. После назначения инвалидируются overview, очередь, реестр, все workspace и кандидаты; выбранная заявка и кандидат очищаются.

## Тексты и состояния

Причины исключения централизованы в `machineryLabels.ts`: известные backend codes получают естественные русские подписи, неизвестные — безопасный текст «Не соответствует требованиям заявки». Raw code в UI не выводится. Пустая очередь сообщает, что заявок, ожидающих решения, нет. При отсутствии подходящих единиц диспетчер различает отсутствие техники вообще и ситуацию, когда возвращены только исключённые единицы, и показывает причины рядом с каждой единицей.

## Тестирование и выпуск

Backend feature-тест сначала воспроизводит расхождение: approved-заявка должна входить и в `requires_decision` API, и в overview, а закрытая — никуда. Admin Vitest-тесты сначала воспроизводят отсутствие формы, permission-gating, stale invalidation, raw reasons и пустые состояния. После GREEN выполняются целевые тесты, PHPStan/Larastan для backend и `tsc --noEmit` плюс ESLint для admin. Backend и admin выпускаются отдельными PR; каждый production deployment запускается только штатным workflow своего репозитория и должен завершиться `success`.

## Решение по mobile

Mobile уже предоставляет прорабу пользовательский сценарий «заявка на технику» в модуле заявок с объекта (`SiteRequestFormScreen`, тип `equipment_request`), а экран Machinery Operations предназначен для полевых операций с назначенной техникой. Текущий дефект — отсутствие admin-формы для существующего asset-request API. Отдельный mobile-релиз не нужен и не входит в scope.
