# Атомарное создание складского актива

## Цель

Создание карточки актива с поэкземплярным учётом должно завершаться либо полностью, либо без появления частично созданной карточки. Пользовательские ошибки должны быть понятными и не содержать внутренних имён полей или технических сообщений.

## Контракт API

Существующий `POST /api/v1/admin/assets` принимает необязательный массив `instances` вместе с `warehouse_id`:

```json
{
  "name": "Шуруповёрт",
  "measurement_unit_id": 1,
  "asset_type": "equipment",
  "accounting_mode": "serialized",
  "warehouse_id": 12,
  "instances": [
    {
      "inventory_number": "INV-001",
      "serial_number": "SN-001"
    }
  ]
}
```

`instances` остаётся необязательным для обратной совместимости. Если массив передан, режим учёта обязан быть `serialized`, склад обязателен, число экземпляров ограничено 50, инвентарные номера обязательны и уникальны внутри запроса. Длины полей совпадают с существующим контрактом приёмки экземпляров: 120 символов для инвентарного номера и 160 для серийного номера и QR-кода.

Существующий `POST /api/v1/admin/assets/{asset}/instances` сохраняется для последующих поступлений и старых клиентов.

## Серверный workflow

Новый сервис приложения оркестрирует существующие `AssetService` и `SerializedAssetReceiptService`. Он открывает внешнюю транзакцию PostgreSQL, создаёт или привязывает карточку и складской остаток, затем создаёт канонические экземпляры, события размещения и проекции реестра техники. Ошибка любого шага откатывает все записи текущего запроса.

Контроллер остаётся HTTP-слоем: получает организацию и пользователя, вызывает workflow и возвращает стандартизированный `AdminResponse`. Ожидаемые доменные и конфликтные ошибки возвращаются без технических деталей; неожиданные исключения логируются с безопасным контекстом, а пользователь получает общее сообщение.

## Поведение админки

Форма передаёт экземпляры в первоначальном запросе создания и больше не выполняет второй запрос после появления карточки. Устаревшее поле «Категория материала» удаляется, поскольку канонические поля — «Категория актива» и «Подкатегория».

Фотографии не входят в транзакцию БД, поскольку сохраняются в S3. Сначала завершается создание актива, затем фотографии загружаются отдельным запросом. При сбое загрузки форма не повторяет создание и сообщает: актив создан, но часть фотографий не загрузилась; пользователь может повторить загрузку из галереи карточки.

Исправляются связанные дефекты формы: очищение исправленной ошибки экземпляров, человекочитаемые названия серверных полей, ограничения длины в инпутах, явный лимит 50 экземпляров и доступная подпись кнопки удаления фотографии.

## Проверки

- PostgreSQL feature-тест доказывает создание карточки и экземпляров одним запросом.
- PostgreSQL feature-тест искусственно провоцирует сбой экземпляров и доказывает отсутствие карточки и остатка после rollback.
- Тесты валидации покрывают количественный режим с `instances`, отсутствие склада, дубликаты и человекочитаемые подписи полей.
- Vitest формы доказывает один атомарный запрос, отсутствие второго запроса экземпляров, очистку исправленной ошибки, частичный успех фотографий и сброс формы.
- После штатного деплоя выполняется production smoke-test через встроенный браузер МОСТ.

## Границы

Миграции, новые очереди и отдельный endpoint не нужны. Лимит первоначального создания — 50 экземпляров, существующая массовая приёмка до 500 сохраняется отдельным endpoint. ИИ-смета не используется.
