# Разбор 14 шаблонов медленных SQL МОСТ за 3 октября 2026 года

Окно исходного отчёта: 00:00–01:30 МСК, 112 медленных выполнений. Средние значения относятся только к событиям, превышающим порог 500 мс. Первая и следующие страницы ресурсных норм образуют два шаблона: вместе 80 выполнений, среднее 17,110 с, максимум 33,502 с.

## Ресурсные нормы

Полный production EXPLAIN без ANALYZE подтвердил материализацию 111199 идентификаторов опубликованных ресурсов под условием `construction_resource_id IS NULL OR ... IN (...)`. Оценка первой страницы — 67410722,22, 131 JIT-функция. Стоимость и JIT-функции не являются измерением времени исполнения.

Для `approved_estimate_norm_resource` необязательный ресурс проверяется коррелированным EXISTS по PK. Обязательная норма проверяется скалярным SELECT EXISTS, сохраняющим проверку сборника, опубликованной версии и соответствия раздела сборнику, до LIMIT. Один EXISTS ресурса снижал оценку до 475833,21, но сохранял JIT и предварительный перебор норм. Обе проверки по ключам дали 25343,23 без JIT для двух диагностических страниц. Production-проверка использовала только EXPLAIN без ANALYZE; фактическое ускорение ещё нужно измерить после выпуска.

Выбор опубликованных версий, критерии успешного импорта и сортировка `finished_at DESC, id DESC` не изменены. NULL-ресурс допустим, ссылка на неопубликованный ресурс исключает строку. Норма из другого типа набора или с разделом другого сборника исключается. Порядок `id ASC` и размер страницы 50 сохранены. В тесте 65 допустимых строк перемежаются недопустимыми; проверяется полный обход двух страниц и соседние каталоги.

## Возвраты приёмки

Старый collection SQL составляет около 128 тысяч символов, 11 медленных выполнений, среднее 2,711 с. Проверки одних родителей повторяются в нескольких ветвях. Для этого типа общие проверки собираются в MATERIALIZED CTE внутри единственного SQL. CTE возвращают только ключи и колонки сопоставления, без содержимого документов. Новая collection SQL имеет 21373 символа.

Область CTE ограничена организацией и соответствующим проектом. Сохранены проверки nullable-родителей, удалённых записей, активной связи организации с проектом, сопоставления родительских ID и самоссылок событий. Общие выборки существуют только в одном запросе; межзапросного кеша нет. Проекция проекта и проверки родителей читают один snapshot, фильтрация выполняется до LIMIT. Сравнение с прежней формой запроса выполняется на корректных операционных данных, защищённых штатными PostgreSQL-триггерами.

## PostgreSQL

Исходные наблюдения: недоступность началась 2 октября в 23:33:30 МСК; pg_postmaster_start_time — 3 октября 00:22:17,292161 МСК. Перезапуск подтверждён, инициатор и причина неизвестны. SQL и JIT не объявляются причиной инцидента.

Во время продолжения работ read-only SSH к приложению восстановился. Узел приложения не перезапускался в рассматриваемом интервале; PostgreSQL расположен отдельно и локальной postgresql.service нет. SSH отдельного узла БД не ответил. Позднее появились новые timeout expired у read-only подключения, таймауты `/up`, `/ready` и postgres-exporter. Повторная внешняя проверка около 02:49 МСК: оба endpoint завершились таймаутом; SSH приложения также не ответил. Успешное TCP-соединение к PostgreSQL не подтверждает успешную авторизацию или выполнение SQL. Новые попытки чтения ограничены временем; зависший собственный диагностический процесс отменён.

Для установления причины нужны журналы PostgreSQL, systemd/kernel и действия провайдера на отдельном узле за 2 октября 23:25 — 3 октября 00:30 МСК. Пользователь БД с SELECT-правами уже существует; новая такая учётная запись не даст журналы ОС. Production-записи, изменение конфигурации и перезапуски не выполнялись.

## Кеш-алерт

Из live API Loki выгружено точное правило MostCacheApplicationError. Все 12 совпадений 00:15–00:30 МСК относятся к PostgreSQL; имя очереди redis_reports встречается внутри failed_jobs. Подготовлен [локальный diff экспортированного правила](most-cache-application-error-2026-10-03.patch). Это diff API-экспорта; физический путь файла правил на отдельном узле мониторинга не предполагается.

Из общей эвристики исключены SQLSTATE и сообщения Connection: pgsql/postgres/postgresql. RedisException и исключения Predis имеют отдельную ветвь, поэтому настоящее исключение Redis обнаруживается даже в сообщении с SQLSTATE. Прежняя эвристика остальных ошибок кеша сохранена. Условия и подписи остальных алертов не изменены.

Проверка реальным LogQL-движком Loki выполнялась только GET-запросами: обе ветви дали ноль на 12 исторических ложных совпадениях; полное metric-выражение принято. Восемь синтетических сообщений проверены через line_format над существующими строками, без отправки логов: RedisException, Predis ConnectionException, ошибка записи кеша, Redis timeout и RedisException вместе с SQLSTATE обнаружены; PostgreSQL с именем Redis-очереди, продолжение такого сообщения и исправный Redis исключены. На сервер мониторинга diff не применялся.

Синтаксис фильтров и объединения проверен по [документации Loki](https://grafana.com/docs/loki/latest/query/log_queries/) и [LogQL reference](https://grafana.com/docs/loki/latest/query/query_reference/). Поведение MATERIALIZED CTE проверено по [документации PostgreSQL 17](https://www.postgresql.org/docs/17/queries-with.html).
