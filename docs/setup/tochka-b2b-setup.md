# Точка: подключение оплаты МОСТ

## Владелец ИП

1. В Точке уточните доступность API для вашего счёта и тариф: получение ежедневных выписок и уведомления `incomingPayment`, `outgoingPayment`. Интеграция не использует эквайринг, СБП, кассу, удалённое выставление счетов или платное ЭДО.
2. Создайте JWT самостоятельно с минимальным правом `ReadStatements`. Для регистрации webhook требуется `ManageWebhookData`; его можно предоставить отдельному временному токену настройки. `ReadAccounts` и получение списка клиентов нужны только для определения идентификаторов, если их ещё нет. Не выдавайте создание/подпись исходящих платежей. Названия и доступность прав сверьте с текущим интерфейсом Точки.
3. Зарегистрируйте webhook на `https://api.xn--1-xtbgmf.xn--p1ai/api/v1/webhooks/tochka`, HTTPS 443, типы `incomingPayment` и `outgoingPayment`. Сервер принимает сырой JWT в теле POST, а не JSON-обёртку. Для проверки подписи используется публичный ключ банка; ваш JWT доступа к API не является ключом проверки уведомлений.
4. Передайте JWT администратору сервера по защищённому каналу. Не присылайте его в чат, задачу, PR, скриншот или лог. Потребуются customerCode, accountId (`номер_счёта/БИК`) и реквизиты получателя; они должны относиться к одному вашему счёту.
5. После настройки проверьте один настоящий небольшой B2B-платёж: счёт PDF, поступление в выписке, однократную активацию, документы. Повторная проверка оплаты не должна менять срок доступа. Сохраните подтверждение и проверьте классификацию дохода в Точке для АУСН.
6. Для подписанных закрывающих документов выберите согласованный ЭДО либо бумажный обмен. PDF в кабинете — копия без подписи. Подключение платного оператора и выпуск УКЭП выполняются отдельно.

## Администратор сервера

Приложение ожидает файл JWT **вне каталога приложения**, например `/run/secrets/most/tochka.jwt`. Каталог закрыт для посторонних; файл доступен только пользователю процесса приложения либо выделенной группе чтения (обычно `0400` или `0440`, в зависимости от UID/GID). Исключите его из Git, image build context, журналов и обычных резервных копий приложения. Секрет должен переживать штатный перевыпуск и быть доступен в API и scheduler только на чтение. После ротации атомарно замените файл; старый токен отзовите в банке.

В текущем Docker Compose общего mount для банковских секретов нет. До включения интеграции администратор должен предоставить этот read-only файл API и scheduler штатным механизмом секретов/серверным override. Простое размещение файла на хосте не делает его доступным в контейнере. Этот выпуск не меняет Compose, pipeline, права на хосте и не создаёт секретный файл.

Проверьте доверие TLS к API банка именно из API и scheduler. При необходимости администратор настраивает доверенную цепочку по [официальной инструкции Точки о сертификате Минцифры](https://developers.tochka.com/docs/tochka-api/certificate). Код использует стандартную проверку TLS; отключать её через `verify=false` или `-k` нельзя. Изменение системного хранилища сертификатов этим выпуском не выполняется.

Настройки приложения, без значения JWT:

```dotenv
BILLING_DEFAULT_PROVIDER=tochka
YOOKASSA_PAYMENTS_ENABLED=false
YOOKASSA_MODE=yookassa_live
TOCHKA_ENABLED=false
TOCHKA_JWT_PATH=/run/secrets/most/tochka.jwt
TOCHKA_CUSTOMER_CODE=
TOCHKA_ACCOUNT_ID=
TOCHKA_SETTLEMENT_ACCOUNT=
TOCHKA_BANK_BIK=
TOCHKA_BANK_NAME=
TOCHKA_CORRESPONDENT_ACCOUNT=
TOCHKA_START_DATE=2026-10-15
```

`YOOKASSA_MODE=yookassa_live` сохраняет корректный транспорт для прежних операций; флаг `YOOKASSA_PAYMENTS_ENABLED=false` и основной провайдер `tochka` запрещают новые платежи. Ключи ЮKassa для банковской оплаты не нужны.

Также заполните существующие `LEGAL_PROVIDER_NAME`, `LEGAL_PROVIDER_STATUS`, `LEGAL_PROVIDER_INN`, `LEGAL_PROVIDER_REGISTRATION_NUMBER`, `LEGAL_PROVIDER_ADDRESS`, `LEGAL_PROVIDER_EMAIL`, `LEGAL_PROVIDER_TAX_STATUS`. Укажите ИП, ОГРНИП и актуальный статус АУСН/НДС. Не подставляйте примерные реквизиты. После проверки файла, доступа контейнеров, банковских прав и всех реквизитов выставьте `TOCHKA_ENABLED=true` штатным способом изменения конфигурации и выпуска.

Штатный планировщик запускает `commercial:sync-tochka --limit=10` каждую минуту. Отдельный cron/worker создавать не требуется. Не запускайте одновременно ручные копии задания. Его результат содержит только readiness, числа обработанных выписок/ошибок и признак блокировки. Ошибка банковского запроса не переключает клиента на ЮKassa.

Адрес ЛК в ответе покупки единиц ИИ использует существующую серверную настройку `FRONTEND_URL`. Для стенда укажите его собственный кабинет. В React-админке отдельный адрес задаётся через `VITE_LK_BASE_URL`; без него production-ссылка доступна только при production API, а на другом API переход скрывается. Изменение этих значений не требует банковских секретов.

## Ежедневный контроль и возврат

- Проверьте ошибки задания сверки и журнал «Банковские поступления МОСТ» в Filament. Операции с неправильным назначением, третьим лицом, изменённым содержимым или истёкшим периодом требуют проверки. Не относящиеся к выручке МОСТ поступления исключайте из сопоставления с обоснованием, сохраняя банковский журнал.
- При запросе возврата проверьте основание и сумму. Согласуйте в журнале «Возвраты оплаты МОСТ». В Точке переведите ровно указанную сумму на исходный счёт плательщика и включите `MOST-R-...` в назначение. Не меняйте получателя. При нескольких исходных платежах будет несколько согласуемых переводов.
- Состояние «перевод подтверждён банком» появится после выписки. Нельзя завершать возврат нажатием кнопки без банковского подтверждения.
- Исходящий «Мемориальный ордер» ещё не подтверждает отправку денег: возврат остаётся в ожидании. Требуется проведённая операция вида «Платежное поручение» с тем же идентификатором возврата, суммой и исходным получателем. Неизвестный вид документа также требует проверки банка.
- Для АУСН проверяйте категории поступлений, ошибочных переводов и возвратов в банке; при расхождениях исправляйте их в предусмотренный банком/ФНС срок. Эта интеграция не отправляет в ФНС налоговые корректировки и не создаёт повторные доходы.

## Вопросы поддержке Точки

1. Доступны ли вашему ИП JWT OpenAPI, `ReadStatements`, `ManageWebhookData` и оба типа webhook? Какова их стоимость на вашем тарифе?
2. Каковы текущие лимиты запросов выписок, сроки их готовности, хранения и повторного получения? В каких случаях `GetStatement` возвращает `Meta.totalPages > 1` и как официально получить все страницы?
3. Подтвердите формат accountId и customerCode именно вашего счёта, наличие `paymentId` и стабильность `transactionId` для проведённых операций, порядок исправлений/сторнирований.
4. Как проверить доставку тестового webhook и ротацию публичного ключа? Требует ли исходящий webhook отдельных настроек?
5. Как правильно классифицировать выручку SaaS, ошибочный перевод, возврат оплаты и переплаты при АУСН «Доходы»? Где владелец должен подтвердить или исправить категорию и до какой даты?

Официальные источники и технические ограничения: [спецификация интеграции](../specs/tochka-b2b-billing.md).
