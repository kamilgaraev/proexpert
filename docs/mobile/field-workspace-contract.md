# Мобильное рабочее место: контекст и персональные действия

Мобильный клиент использует `/api/v1/mobile` того же Laravel-приложения. Все методы требуют мобильную авторизацию и организационный контекст. Права проверяются для организации, выбранного объекта и конкретной записи на сервере; название роли не является условием доступа.

## Доступные разделы

`GET /modules?project_id=123` возвращает `data.modules` и `data.meta`. `project_id` можно опустить для организационных разделов. При выборе другого объекта клиент повторяет запрос и строит меню из нового набора разрешённых модулей. Недоступный пользователю объект возвращает `403`.

Каждый модуль содержит `slug`, `route`, `title`, `description`, `icon`, `supported_on_mobile`, `order` и `permissions`. Клиент использует `permissions` для видимости действий; сервер проверяет права повторно при выполнении действия.

## Мои действия

`GET /my-actions?project_id=123&page=1&per_page=10` возвращает назначенные пользователю записи. Без `project_id` учитываются все доступные объекты текущей организации. Ответ списка имеет общий формат:

```json
{
  "success": true,
  "data": [
    {
      "id": 42,
      "type": "site_request",
      "route": "site_request",
      "title": "Материалы на объект",
      "status": "pending",
      "project_id": 123,
      "project_name": "Объект",
      "due_at": "2026-09-30",
      "allowed_actions": ["change_status"]
    }
  ],
  "meta": {"current_page": 1, "last_page": 1, "total": 1}
}
```

Агрегируются назначенные заявки объекта, заявки на закупку, задачи графика, замечания по качеству и ожидающие решения по платежным документам. Для заявки на закупку `id` — ID заявки, `type` и `route` равны `purchase_request`; карточка открывается через `GET /api/v1/mobile/procurement/purchase-requests/{id}`. Учитываются записи, связанные с заявкой объекта, назначенные текущему пользователю и не находящиеся в статусе `draft`, `rejected` или `cancelled`. Для платежного документа `id` — ID документа, `type` и `route` равны `payment_document`; карточка открывается через `GET /api/v1/mobile/payments/documents/{id}`. Она попадает в список при персональном назначении или открытом шаге согласования по праву `payments.transaction.approve`, состоянии согласования `pending`, доступе к объекту и праве `payments.invoice.view`. `allowed_actions` содержит `approve` и `reject` только при отдельных правах и ожидающем решении. `route` указывает тип карточки для прямого перехода. `per_page` ограничен сервером. Для каждой записи сервис проверяет организацию, доступный объект, назначение и право просмотра; `allowed_actions` содержит только действия, разрешённые в её состоянии.

## Персонал объекта

`GET /field-admin/personnel/employees`, `/absences` и `/orders` принимают `project_id` выбранного объекта. Состав определяется действующими назначениями сотрудников на объект; сервер проверяет право `workforce.view` в строгом контексте объекта. Карточка сотрудника принимает тот же параметр и не открывает запись другого объекта.

`GET /field-admin/personnel/attendance?project_id=123&work_date=2026-09-23&page=1&per_page=20` показывает статусы по табелю, подтверждениям QR и отсутствиям. `source_label` сообщает источник статуса: плановая явка и подтверждённая отметка не смешиваются. Ответ содержит `data` и `meta`.

## Общий формат списков

Для новых мобильных реестров элементы находятся в корневом `data` (массив), а `meta` — рядом с ним. Клиент передаёт фильтры и номер страницы серверу и загружает следующие страницы по `meta`. Ошибка возвращает `success: false`, `message`, `data: null`, `code` и при необходимости `errors`.

## CRM в поле

`POST /catalog/crm/activities` создаёт заметку или следующий контакт через общий CRM-сервис. Тело содержит `kind` (`note` или `next_contact`), `target_type` (`company`, `contact`, `lead`, `deal`), `target_id` (UUID), `subject`, необязательный `body` и `due_at` для следующего контакта. Требуется `crm.activities.create`; запись CRM и, для сделки, её объект проверяются в сервисе. Автор и ответственный — вошедший пользователь. Ответ `201` содержит созданную активность в `data`.

## Подтверждение трудозатрат

`GET /api/v1/mobile/time-tracking/pending-approvals?project_id=123&page=1&per_page=20` возвращает отправленные записи времени по доступному объекту. Каждый элемент содержит `available_actions`, сформированный сервером отдельно по `time_tracking.approve` и `time_tracking.reject`. `POST /api/v1/mobile/time-tracking/entries/{id}/approve` подтверждает запись, `POST /api/v1/mobile/time-tracking/entries/{id}/reject` отклоняет её с обязательной `reason`. Сервер повторно проверяет организацию, доступ к объекту, отдельное право и состояние `submitted`, затем вызывает общий workflow учёта времени. Записи в иных состояниях отвечают `409`; юридические и платёжные процессы не затрагиваются.
