## Главный продуктовый приоритет: проверяемое инженерное знание

Автоматическая проверка и накопление инженерных знаний — один из основных результатов разработки МОСТ наряду с корректными числами и универсальным составом работ. R05 и R07 образуют обязательный сквозной результат, а не необязательное улучшение рекомендаций после остальных функций. Агент A берёт его сразу после защитного R02; B предоставляет существующие проверки единиц, расчётов, нормативов и цен. Полная иерархия R06 не должна блокировать первый пилот неизвестной технологии в одной текущей сущности.

Обязательный сценарий: **неизвестная технология → конкретный вопрос человеку → ответ и документы → автоматическая независимая проверка → сохранение подтверждённого знания → повторное использование с проверкой применимости**.

| Этап | Использовать существующее | Обязательная проверяемая граница |
| --- | --- | --- |
| Найти пробел и спросить | ProjectModel facts/evidence, Planning, Questions, доступные нормативы/Learning/RAG | Сначала проверить текущие знания/проект; вопрос содержит недостающий параметр, единицу и влияние. Не подставлять домовую технологию |
| Принять ответ и документы | Текущие upload/source hash/version, SaveManualProjectFacts для numeric parameter, AnswerEstimateClarification для его enum-вопросов, Decision | Ответ — scoped user-confirmed claim; документ связан с сущностью, решением и source revision. Не превращать доверие пользователя в инженерную достоверность |
| Проверить автоматически | Имеющиеся numeric/unit/norm/applicability gates, документы проекта/производителя и независимые нормативные источники | Для конкретного claim зафиксированы исходы passed/unresolved/failed и источники. Проверяется независимое основание, актуальность, размерность, арифметика и условия; согласие другой LLM не доказательство |
| Сохранить | Существующие Fact/Evidence/Decision и LearningExample/context/source refs; штатный RAG source | Различимы автоматически проверенный claim, подтверждение пользователем, непроверенный и отклонённый. Нет автоматического global rule или публикации текста ответа как verified |
| Применить повторно | Existing Learning reader/matcher; RAG ищет кандидатов, но retrieval не даёт допуска к расчёту | Целевая граница допуска: повторно проверить authoritative запись, org/project scope, объект/технологию/условия, единицы, редакцию нормы и source hash/revocation. Исторический объём не заменяет текущий расчёт. Текущий общий RAG-ассистент эту проверку не выполняет; его предел отдельно указан ниже |

Если независимого источника/условия нет, сохранять unresolved/candidate и задавать следующий конкретный вопрос; отсутствие доказательств не означает ошибку. Пользователь может принять локальное ограниченное допущение, но оно не становится переносимым проверенным знанием. Автоматически можно доказать конкретную арифметику/размерность/соответствие документу; инженерную применимость нельзя объявлять доказанной одной формальной проверкой.

Обязательная приёмка R05+R07 — одна неизвестная технология без специального handler (например, монтаж установки по технической спецификации), полный положительный путь и отрицательные случаи: недостаточный источник, противоречие единиц/условий, вторая LLM без evidence, новая редакция нормы, другой объект и другая организация. Нужны runtime-проверки записи и повторного чтения, а не только тест смены label. Первый повтор в совместимом контексте предлагает проверенный claim с объяснением; несовместимый/устаревший контекст требует новой проверки. Фиксировать, какие проверки были replay/mocked и какие прошли на реальных документах/каталоге.

### R01. Проверять физическую допустимость геометрии

- **Проблема/доказательство:** F01, E07 — confirmed стена 10×3 минус проём 4×4 даёт confirmed 14 м² без issues. Происхождение/положительный остаток не доказывают допустимость формы.
- **Польза:** противоречивый чертёж или ввод вызывает понятный вопрос вместо правдоподобного неверного объёма.
- **Минимум:** добавить проверки совместимых форм/осей/габаритов в текущую derivation boundary. При отсутствии данных возвращать unresolved/review; не обрезать геометрию молча. Объяснить, какие измерения нужны. Не создавать общий CAD solver ради этого дефекта.
- **Владелец/зависимости:** B, самостоятельно; A согласует тип вопроса/ошибки без изменения смысла confirmed.
- **Приёмка:** regression выше/шире родителя; допустимый граничный проём; положительный остаток при невозможном child; дубли и, при наличии координат, пересечение. Pure factory не возвращает confirmed для невозможного случая; существующие корректные примеры сохраняются. В разрешённом integration fixture derivation→draft→apply нельзя применить устаревший/недопустимый quantity proof. Проверять новый результат пересчётом, не только текстом warning.

### R02. Убрать молчаливую домовую подстановку для неизвестного объекта

- **Проблема/доказательство:** F02, E06 — bridge/school/hospital/custom получают house packages; selected_sections лишь фильтрует их. bridge/equipment даёт пустоту без подтверждения полноты.
- **Польза:** система честно работает с неизвестным и сохраняет найденные элементы/спецификации, задаёт предметные вопросы.
- **Минимум:** в `PackagePlannerService`/`WorkPlanCompiler` выделить явный unknown/evidence-driven исход. House branch разрешать по подтверждённой residential классификации. Свободный текст понимает существующий LLM/Understanding, код проверяет его структуру и основания; regex NLP не расширять. Сначала подтвердить фактический путь и переиспользовать текущий вызов/результат без второго ИИ-контура. При отсутствии надёжного понимания использовать уточнение. Reuse известного элемента возможен независимо от типа целого объекта; не заменять ошибку двадцатью новыми if/template.
- **Владелец/зависимости:** A; главный агент утверждает статус unknown и смысл completeness, B сохраняет guards нормативов/объёмов.
- **Приёмка:** table-driven negative cases 20 типов + совершенно новый synthetic type; неизвестный не получает домовые работы/`document_backed` без evidence. `structures` не подменяет мост кладкой и окнами; «Монтаж стендов» не даёт walls. Неоднозначный/неразрешённый состав даёт request_info без выдуманных работ; отдельное невалидное предложение уходит в quarantine, сбой провайдера/формата всего ответа сохраняет failed run без ручного NLP fallback; несколько структурированных intents имеют разные понятные названия и identity. Known house/warehouse/industrial и document-only regressions сохраняются. По проверенной спецификации неизвестного объекта можно включить обоснованную работу с источником; цена/объём не возникают из типового профиля. Число LLM-вызовов проверено; неизменный вход не требует ненужного повторного понимания.

Фактическая причина R02 (head e5e5fa): `G/Pipeline/Stages/UnderstandObjectStage.php:28–33` всегда вызывает ручной parser; `UnderstandDocumentsStage.php:25–29` собирает manifest. Ранний ProjectUnderstandingCoordinator выбирает уже подготовленные связи и конфликты, не выдаёт новые работы. `G/Pipeline/Stages/PlanWorkItemsStage.php:105–107` сначала компилирует кандидатов, а `:155–176` затем вызывает существующий Composer. `G/Analysis/Composition/RunEstimateComposer.php:189–205,304–309` сохраняет каждого серверного кандидата даже при молчании модели: один prompt не может удалить ложные walls.

### R03. Согласовать экспорт и принятую расчётную проекцию

- **Проблема/доказательство:** F03, E13 — CSV отбрасывает catalog-only work без нормативной привязки; CSV/JSON обходят selected projection, raw summary берёт base.
- **Польза:** выгрузка соответствует выбранному пользователем составу и сумме.
- **Минимум:** использовать существующий `ReadConfirmedEvaluationExport`/confirmed projector для пользовательских финансовых экспортов; сохранить разделение нормативной и коммерческой строки. Определить JSON как confirmed estimate либо явно обозначенный technical draft с версией/смыслом. Не добавлять второй калькулятор.
- **Владелец/зависимости:** B; главный агент фиксирует формат/совместимость, A/UI consumer принимает согласованную семантику.
- **Приёмка:** catalog-only, normative-only и mixed fixtures; сценарий, отличный от base; одинаковый выбранный состав и net-суммы позиций у CSV/XLSX/apply. НДС, резерв и итог к оплате сравниваются отдельно, если представлены форматом; net нельзя приравнивать gross. JSON соответствует объявленному контракту. Stale/unconfirmed projection не выдаётся за подтверждённую. Сохранить escaping CSV и scope/permissions. Включить тест controller branching, а не только exporter helper.

### R04. Создать доказательный baseline в существующем acceptance-контуре

- **Проблема/доказательство:** 227 pure PHP + 240 frontend tests не являются полным запуском; browser estimator E2E не найден; `EvaluationReleaseGate` лишь проверяет наличие reviewed corpus (E15, E18).
- **Польза:** новый чат и команда видят воспроизводимый результат по позициям и знают границы точности.
- **Минимум:** подготовить инженерно проверенные fixtures и approved immutable manifest для текущего Benchmark/Acceptance, записать версии engine/dataset/prices/source hashes. Начать с известных элементов + unknown negative + изменения; обязательный ранний pilot R05/R07 проверяет весь цикл инженерного знания, затем расширить до трёх пилотов из universality. Не писать новый evaluation framework. Corpus-readiness и accuracy-report назвать раздельно.
- **Владелец/зависимости:** главный агент — oracle/общие критерии; A — состав/вопросы/изменения; B — объёмы/нормы/деньги. Защитные R01/R02/R03 до положительной приёмки соответствующих путей. Комплексный pilot после R06. Изолированный runtime должен быть отдельно разрешён правилами следующей задачи; production не используется.
- **Приёмка:** сохранённые команды и результаты HTTP→upload/unit→ProjectModel→planning→quantity→norm/resources/price→review→export/apply→обычная Estimate. Mock/replay, реальный parser и live provider отмечены отдельно. Oracle содержит состав, единицы, источники, ожидаемые неизвестности и tolerances; повтор даёт воспроизводимые числа при тех же pins. Проверены stale decision, duplicate request/job, cross-org denial и refresh UI. Reviewed label/ответ LLM не заменяет независимый инженерный oracle.

### R05. Изолировать запись и ограничить повторное применение знаний доказательствами

- **Проблема/доказательство:** F05, E14–E15 — unit_unverified импорт даёт positive boost; версия нормы не участвует в reuse; автоматическая проверка неизвестного ответа не замкнута. Дополнительный F07/R07 RED 1/10: null-ID writer identity не включает org/project/session/work key и допускает коллизию разных организаций.
- **Немедленный P0:** scoped null-ID lookup в текущем Recorder, fail closed при неполной fallback identity; без новой schema/non-null identity. Пользователь не теряет и не загрязняет знания другой сессии/организации. Приёмка: две org, две session, два work key одной нормы в одной session, replay 1→0 с неизменной чужой строкой; старые non-null recorder cases проходят. A — единственный автор; независимо от нормативных расширений B. Историческую/production очистку не запускать.
- **Польза:** ошибка/устаревший пример не усиливает будущие рекомендации; подтверждение человека остаётся полезным с понятной областью.
- **Минимум:** расширить текущие Decision/LearningExample metadata/read gates, не создавать Memory v2. Разделить candidate/user_confirmed/source_supported/independently_reviewed/rejected; автоматические проверочные результаты хранить отдельно от авторства подтверждения. Исходные quality/confidence не считать инженерной вероятностью. Проверять unit, source revision, dataset version, применимость и отзыв до автоматического positive boost; stale пример сохранять как объяснимый аналог. Существующий RAG возвращает кандидатов/источники, а допуск к reuse читает authoritative запись и её текущие доказательства.
- **Владелец/зависимости:** A; trust-контракт утверждает главный агент. B определяет результаты deterministic unit/arithmetic/norm checks. R04 даёт регрессии; сами unit/version gates можно сделать раньше.
- **Приёмка:** unit_unverified не повышает current confidence; old version с тем же norm_code требует новой проверки; negative/revoked не реанимируется; пользовательское «да» и вторая LLM не повышают уровень до independent. Другой org не читает пример; project-local данные не превращаются в global rule; исторический объём не заменяет derivation. Существующий импорт и запись feedback остаются идемпотентны. R05 не считается завершением стратегического результата без runtime-сценария R07: ответ/документ, независимые checks, запись подтверждённого claim и безопасное повторное применение.

### R06. Добавить область сооружения/системы без второй модели проекта

- **Проблема/доказательство:** E04/E06, F02 — один objectType и плоские package keys; дом+гараж+баня не образуют отдельные здания. Геометрические/evidence связи уже есть. R07 native lifecycle дополнительно подтвердил смену canonical entity ID при source_version a→b даже с тем же native stable key: `BuildingModel/ProjectModelEvidenceWriter.php:224` включает sourceVersion в ID, `Domain/ProjectModel/EloquentProjectModelRepository.php:32–38` ищет stable key внутри точной source version. Перенос контекста между версиями пока не доказан.
- **Польза:** комплекс содержит раздельные здания/установки/сети и связанные сметы без смешивания и двойного счёта.
- **Минимум:** уточнить identity/parent scope в текущих Entity/Fact/Quantity/Work/Package и проекторах; явный владелец shared site/system work. Добавить необходимые связи и validation в существующую canonical boundary. Общую модель relations проектировать только в объёме трёх pilots; геометрический/evidence DAG переиспользовать по назначению.
- **Владелец/зависимости:** A, главный агент утверждает ключи/совместимость. B адаптирует resolver/proof/norm-price consumers по контракту, не меняет identity самостоятельно.
- **Приёмка:** два корпуса с одинаковыми именами комнат/работ/кровель не объединяются; общая сеть учитывается один раз; entity нельзя привязать к чужой org/project/session/несовместимому parent; недопустимые циклы ownership отклоняются. Повторное чтение/пересборка сохраняет stable IDs. Старый однообъектный fixture проходит без изменения чисел.

### R07. Замкнуть работу с неизвестной технологией

- **Проблема/доказательство:** E05/E14 — versioned catalog applicability есть, но Stage5 рекомендации фактически три кровельные системы; generic equipment строки не описывают всю технологию монтажа.
- **Польза:** доильная установка, медицинское или промышленное оборудование обрабатывается через проверяемые сведения, а не через догадку/отказ всего проекта.
- **Минимум:** в текущих coordinator/questions/composer использовать typed технологический intent со specification, условиями и зависимыми работами; извлекать сведения из project/current catalog/доступных знаний, спрашивать конкретные пробелы. Проверки единиц/расчётов/норм делегировать B, источники производителя/проекта фиксировать evidence. Unverified ответ остаётся локальным допущением, не общей технологией.
- **Владелец/зависимости:** A, B — независимые проверяемые predicates; R02/R05. Первый однообъектный knowledge pilot не требует новой общей иерархии; для комплекса R06. Один equipment pilot вместо нового семейства специальных handlers.
- **Приёмка:** неизвестная установка + неполная спецификация → конкретный вопрос; документ/ответ → автоматические независимые source/unit/arithmetic/norm/applicability checks с явными исходами; конфликт → review с причиной. Подтверждённый claim записан существующим контуром, повторно найден и предложен совместимому объекту с проверкой актуальности/контекста и ссылками на доказательства. Есть source lineage и раздельный user-confirmed/automatically-checked смысл; без доказательств нет auto publication/reuse. Технологические зависимости монтажа/коммуникаций/ПНР проверены независимым oracle; другой контекст, stale source и другая org не получают слепого reuse. Покрыть положительный и отрицательные paths всего сценария, а не только catalog recommendation.
