# Бюджетная защита AI-сметчика: production recovery

## Контекст

Документ 176 с лимитом 600 ₽ был поставлен на паузу при фактическом расходе 20,796345 ₽. Причина — физическая попытка арбитра страницы 3 осталась в `wire_started` без журнала usage на границе deploy. Текущий guard трактует любую такую строку как безусловное достижение лимита.

## Контракт

- Лимит документа ограничивает совокупный фактический и зарезервированный расход документа, а не верхнюю оценку всей оставшейся очереди.
- Перед каждым новым физическим сетевым вызовом в одной транзакции блокируются session и document, суммируются подтверждённые usage и активные reservations, затем добавляется верхняя граница только следующего вызова.
- Вызов разрешён, если итоговая проекция не превышает лимит; при превышении документ ставится на паузу до отправки запроса.
- Reservation хранится на physical attempt и не создаётся при replay `response_received`/`completed`.
- Для legacy `wire_started`/`ambiguous` без reservation используется одна консервативная верхняя граница вызова. Такая строка не становится автоматически `cost_limit_reached`.
- Session guard агрегирует фактические расходы и reservations всех документов одной сессии. Неоценённый usage вне поддерживаемого physical-attempt контракта остаётся fail-closed.
- Операции stop, breaker, ABAC, idempotency, durable replay и source/lineage/version fences сохраняются.

## Recovery документа 176

- Явное действие пользователя снимает прежнюю ложную паузу без увеличения лимита 600 ₽ и без увеличения confirmation version, если текущая проекция помещается в существующий лимит.
- Готовые страницы 1–2 и три completed observer run страницы 3 переиспользуются.
- Legacy arbiter `wire_started` без durable response обозначается `ambiguous` и не вызывается повторно.
- Продолжаются только queued units текущих source version и lineage; PDF повторно не загружается.
- Read model с paused document обязан показывать session как `input_review_required` и действие продолжения, а после явного действия — согласованное processing-состояние.

## Проверки

- 20,796345/600 не создаёт паузу.
- Граница ровно 600 разрешена; проекция выше 600 блокируется до wire.
- Параллельные reservations сериализуются блокировками.
- Session budget учитывает несколько документов.
- Durable response replay не создаёт provider call.
- Production-shaped recovery сохраняет уже оплаченные результаты и текущий source/version.
- Backend contract и admin MSW подтверждают paused/resume и согласованные статусы.

## Ограничения релиза

После deploy выполняются только `/ready`, проверка release SHA, protected 401, read-only состояние session 74/document 176 и проверка новых ошибок. Retry/resume и любые платные AI-вызовы выполняет только пользователь.
