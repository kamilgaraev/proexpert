# Фильтр остатков по складской зоне

## Проблема

Экран остатков предлагает выбрать складскую зону, но отправляет её код как точный `location_code`. У размещённых остатков `location_code` содержит код ячейки, поэтому выбор зоны скрывает позиции, которые визуально находятся в этой зоне.

## Контракт

- Admin UI передаёт `zone_id` в `GET /api/v1/admin/warehouses/{warehouseId}/balances`.
- Backend принимает `zone_id` как целое значение и отбирает партии, связанные с ячейками выбранной зоны.
- Для исторических партий без `cell_id` сохраняется совместимость: партия включается, если её `location_code` совпадает с кодом ячейки выбранной зоны.
- Организация и склад остаются обязательными границами выборки; чужая зона не раскрывает данные.
- Устаревший точечный фильтр `location_code` сохраняется для существующих потребителей API.

## Состояния UI

- В списке зон используются стабильные идентификаторы, а пользователь продолжает видеть код и название зоны.
- После выбора показываются только количества, реально находящиеся в выбранной зоне.
- Пустой результат и сброс фильтров используют существующие понятные состояния.
- Подписи «Тип актива» и «Зона / адрес» программно связаны со своими полями.

## Проверки

- Backend: актуальная партия с `cell_id`, историческая партия с кодом ячейки и партия другой зоны.
- Frontend: выбор зоны отправляет `zone_id`, не отправляет код зоны как `location_code`, селекты доступны по видимым подписям.
- Production: выбрать `STORAGE-A` на основном складе и убедиться, что размещённые позиции не исчезают.

## Риски

- Агрегированные количества после фильтра относятся к выбранной зоне, а не ко всему складу; это соответствует назначению фильтра «Зона / адрес».
- Фильтрация по зоне не должна менять семантику точечного фильтра ячейки или кода локации.
