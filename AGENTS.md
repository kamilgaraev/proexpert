# Инструкции репозитория backend/API МОСТ

## Область действия и приоритет

- Эти правила действуют во всём репозитории. Более вложенный `AGENTS.md` может уточнять их только для своей директории.
- Продукт называется **МОСТ**. `prohelper` — только техническое имя репозитория.
- Всегда общайся с пользователем на русском языке, деловым и технически точным стилем.
- Перед правкой учитывай существующие локальные инструкции в `.agent/rules/`, но при конфликте следуй этому файлу и прямому запросу пользователя.

## Безопасный процесс работы

- Не работай напрямую в `main`: обнови локальный `main` из `origin/main` только безопасным fast-forward, создай отдельную ветку и передавай изменения через Pull Request.
- Не коммить, не отправляй ветку, не создавай PR, не выполняй merge или deploy без отдельной явной команды пользователя.
- Не изменяй и не откатывай чужие правки. Перед началом проверь ветку и `git status`; при неожиданных изменениях остановись и сообщи пользователю.
- Не используй опасные или разрушающие локальные команды: `git reset --hard`, принудительный checkout чужих файлов, рекурсивное удаление широких путей, очистку неотслеживаемых файлов и иные необратимые операции без прямого разрешения.
- Не изменяй CI/CD, GitHub Actions и deployment-конфигурацию без отдельного прямого запроса.
- Не добавляй в Git `.env`, ключи, токены, пароли, production-данные, локальные пути пользователя, логи, кеши, `vendor`, `node_modules` и другие зависимости или генерируемые артефакты.

## Production и окружение

- Считай работу локальной. Не предполагай наличие production-доступа и не создавай SSH-ключи или иные учётные данные.
- Production-диагностика разрешена только после отдельной явной выдачи владельцем проекта read-only доступа для конкретной задачи. До этого запрашивай у пользователя обезличенные логи или другие необходимые данные.
- Даже с read-only доступом запрещены `root`, `sudo`, миграции, запись в БД и файлы, очистка кешей, перезапуски, очереди и любые операции с побочными эффектами. Не читай и не раскрывай секреты.
- Локально не запускай `php artisan migrate*`, `db:*`, `tinker`, сидеры, rollback/reset/delete и любые команды, обращающиеся к БД, без явной команды пользователя с указанием окружения.
- Не запускай dev-серверы и сборки без необходимости и прямого согласования.

## Архитектура Laravel

- Стек проекта: PHP 8.2, Laravel 11, PostgreSQL. Соблюдай PSR-12; во всех новых PHP-файлах используй `declare(strict_types=1);`.
- Сохраняй архитектурные границы: Controller отвечает только за HTTP, FormRequest — за входную валидацию, Service — за бизнес-процесс и транзакции, Repository/Query service — за сложные или повторно используемые запросы, DTO/Result — за межслойные контракты, Resource/mapper — за API-представление.
- Контроллеры должны быть тонкими. Не добавляй в них бизнес-расчёты, транзакции, сложные запросы, прямые доменные CRUD-операции или сборку больших payload. При касании старой логики выноси затронутую часть минимальным безопасным шагом.
- Размещай доменную функциональность в подходящем модуле `app/BusinessModules`; взаимодействие модулей организуй через публичные сервисы и интерфейсы, а не прямой доступ к внутренним таблицам другого модуля.
- Сервис обязан самостоятельно проверять organization/project/ownership scope и права actor-а. Клиентские проверки, middleware и проверки только в контроллере не являются достаточной защитой.
- Для связанных ID используй scope-aware валидацию. Роли и права определяй только в `config/RoleDefinitions/{context}/{role_slug}.json`, не хардкодь их в PHP; проверки выполняй через `AuthorizationService` и существующий `RoleMiddleware`.

## API, переводы и данные

- Используй стандартный класс ответа по потребителю: `AdminResponse`, `MobileResponse`, `LandingResponse` или `CustomerResponse`. Не возвращай из контроллеров произвольный `response()->json()` и не раскрывай пользователю технические исключения.
- Пользовательские сообщения в PHP переводи через `trans_message('file.key')`; не используй `__()` напрямую и не хардкодь русский текст без редкого обоснованного исключения.
- При создании или переименовании permissions добавляй русские названия прав и групп в `lang/ru/permissions.php` и проверяй, что UI не получает технические ключи вместо подписей.
- Логируй ошибки с безопасным контекстом, без секретов и чувствительных данных. Пользовательский текст должен быть понятным и не содержать внутренних терминов.
- Для файлов используй S3 через `App\Services\Storage\FileService` и пути внутри `org-{organization_id}/...`; не сохраняй доменные файлы на локальный диск.
- Для PostgreSQL учитывай constraints, внешние ключи, индексы, N+1, транзакции и реальный production-объём. Миграции создавай только как код и никогда не запускай без прямого разрешения.

## Проверки и документация

- Выбирай проверки по риску. Для документации и текстов не запускай сборки и автотесты; проверь diff, структуру Markdown, UTF-8 и отсутствие секретов.
- Для исполняемого PHP запускай после логического блока минимальный релевантный PHPStan/Larastan и целевые тесты затронутого модуля. Не повторяй неизменившиеся успешные проверки.
- При изменении API-контракта, прав, валидации, хранения или бизнес-процесса добавляй целевую или регрессионную проверку и оцени обратную совместимость со всеми клиентами МОСТ.
- Если задача заметно меняет workflow, роли, статусы или операционный сценарий, проверь необходимость обновить бизнес-понятную workflow-документацию. CI/CD в такую работу не включай без отдельного запроса.
- В финальном ответе перечисли изменённые файлы, выполненные проверки и проверки, которые не запускались, с краткой причиной.
